# 现场演示与验收清单

## 准备

- [ ] 三台电脑都能在项目目录运行 `python -m flight_system.client --help`。
- [ ] A 运行服务器，B/C 使用 A 的局域网 IP，而非 localhost。
- [ ] 网络允许 UDP 到达服务器和客户端，已排除无线客户端隔离。
- [ ] 保存一份提交版本，演示前不临时替换协议或大改代码。

## 正常功能：at-most-once，无模拟丢包

- [ ] SEARCH Singapore → Tokyo 返回 101 和 102。
- [ ] DETAILS 101 返回 UTC 时间、浮点票价 500、座位 10。
- [ ] 查询不存在的航班或航线显示错误。
- [ ] 订座 2 个后余量 8；订 0、负数、超额均报错且余量不变。
- [ ] 连续两次 SET_FARE 到 700，票价仍是 700。
- [ ] 连续两次 DELAY 10 分钟，时间累计延后 20 分钟。

## 回调

- [ ] B 监控 101，60 秒；C 对 101 订座；B 自动收到余量。
- [ ] C 对 102 订座，B 不收到 101 以外航班的通知。
- [ ] 再开一个监控客户端，同时监控 101，两个订阅者均收到更新。
- [ ] 到期后继续订座，服务器不再向已到期订阅发送 CALLBACK。
- [ ] 监控结束后客户端可以继续查询和退出。

## 调用语义对比：每轮重启服务器、启动新客户端

先用 `--semantics at-least-once --drop-replies 1`，客户端首项操作订 101 的 2 个座位：

- [ ] 首次执行、丢回复、重传、再次执行依次出现在日志中。
- [ ] 初始 10 座最终变 6 座。

再用 `--semantics at-most-once --drop-replies 1`，重复同样操作：

- [ ] 第二次请求命中缓存 `CACHE_HIT`。
- [ ] 初始 10 座最终变 8 座。

补充解释：

- [ ] 丢请求与丢回复发生在不同位置；只演示丢请求不足以证明重复执行问题。
- [ ] 默认总尝试次数为 4，不是“首次发送加 4 次重试”。
- [ ] 全丢回复时客户端显示 unknown，不能断言服务器没执行。
- [ ] 设置票价是幂等，延后起飞是非幂等；去重不改变业务操作本身的分类。
- [ ] 内存缓存不保证服务器重启后去重，通知本身不是可靠传输。
